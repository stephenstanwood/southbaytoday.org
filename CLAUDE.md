# southbaytoday.org

## Architecture
- Astro 6 + Vercel + React + Tailwind v4
- Standalone app broken out from stanwood.dev
- Single page (src/pages/index.astro) with tab-based navigation
- All SBS components in src/components/south-bay/
- Static data in src/data/south-bay/ (generated by scripts/)
- Shared lib in src/lib/south-bay/

## Styles: one token set, one chrome, area sheets
- `src/styles/sbt/tokens.css` holds every color, radius, shadow, and font token (`--sb-*`). Reach for these instead of hard-coding hex values or one-off radii.
- `src/styles/sbt/chrome.css` holds the masthead, nav, footer, page hero, and section heads. It also holds the shared building blocks: `.sb-btn` (the house pill button), `.sb-chip`, `.sb-card`, `.sb-skeleton`, and `.sb-empty`.
- Per-area rules live in `home.css`, `events.css`, `gov.css`, `tech.css`, `camps.css`, `food.css`, and `city.css`. `BaseLayout.astro` loads all of them site-wide (lazy tab chunks can't inject CSS into a prerendered head), so class names must stay area-prefixed.
- Every page wears the same header and footer: `Masthead.tsx` and `SiteFooter.tsx`. That covers the app tabs, `CalendarShell` static pages, and city pages. Don't fork them per page.
- House rules from the 2026-09 overhaul:
  - No red UI. Hot states and warnings use amber, rust, or coral.
  - Body text ≥14px and meta ≥12px. Nothing at 7–9px.
  - Cards use `--sb-radius-md` with a hairline `--sb-line` border.
  - Tap targets ≥40px on phones.
  - Views keep their first render free of clock, random, and localStorage reads (refine in `useEffect`) so hydration matches. When "today" has to be in the static HTML, read it through `useTodayPT(buildDayPt)` (or `useClockValue` for a value that doesn't turn over at Pacific midnight). `SignalShell` hands the tab islands that need them the build's day (`buildDayPt`) and moment (`buildTimeMs`), so the page hydrates as built and then switches to the reader's clock.
  - Islands ship every import to every page that uses them. Don't import all-city JSON into a per-city island. Slice it in the page's frontmatter and pass props, or serve a per-city JSON file for data the island only uses after mount. `CityPage` shows the pattern (`lib/south-bay/cityPageData.ts`, `/city/<slug>/open-now.json`). Importing `open-now-candidates.json` directly once made its chunk 150 KB gzipped.
  - Move repeated inline `style={{}}` objects into the area sheet.

## Data Generation
Run these scripts to refresh pre-generated data:
- `npm run generate-digests` — council meeting summaries (needs ANTHROPIC_API_KEY)
- `npm run generate-events` — upcoming events from 20+ sources
- Event refresh reliability and recovery: `docs/event-source-refresh.md`
- See `package.json` for full list of `generate-*` scripts

`/event/<slug>` URLs derive from date + title, so re-titling an event (typo
fix, dedupe swap, source rename) changes its URL. `events-retired.json` records
every future slug that leaves the feed; the build 301s each one to its
successor or keeps it resolving as a noindex "no longer listed" leaf.
`generate-events` and the tracked pre-commit hook maintain the ledger — if you
edit titles some other way, run `npm run sync-event-slugs` before committing.

## Day plans: quality-first pillar pairs

The canonical plan model is `pillar-pairs-v1`: select the best morning,
afternoon, and evening activities before considering food, then attach a great
breakfast/lunch/dinner within 5 miles of each pillar. Regional plans may span
three towns; geography across pillars is irrelevant and must not become a
clustering, anchor-city, route, or diversity objective. `/city/<slug>` is the
only `scope: "city"` consumer. Every other surface uses `scope: "regional"`.

The six cards are three atomic pairs with reciprocal `pairedWithId` metadata.
Never drop, carry forward, or manually swap one card in isolation. The full
contract and consumer map are in `docs/day-plan-selection.md`. Chains may
qualify, but only when the specific branch is new, distinctive, exceptionally
well-regarded, or editorially notable; a generic branch is filler.

Baked blurbs drift: the 3:21 AM cron bakes `place-blurb-cache.json` wording into
`default-plans.json`, so a cache fix that lands later the same morning leaves the
day's card stale (Sep 16 and Sep 17 both hit this). After editing the cache, run
`npm run check-plan-blurbs -- --fix` and commit the re-baked plans.

The homepage bakes `default-plans.json` at build time, so plans reach readers
only once they are on origin/main. The Mini's `org.southbaytoday.default-plans-refresh`
(`scripts/social/scheduled-default-plans.mjs`, 3:20 AM with a 3:30 retry)
generates, commits, and pushes them under the repo lock. A rerun is a no-op once
today's plans are published; `--force` regenerates.

## Mini launchd agents: node runs under /bin/zsh
Tracked plists launch `/bin/zsh -f -c '/opt/homebrew/bin/node <script>; exit $?'`,
never Homebrew's node as the program. After `brew upgrade node` (the Sunday
3:20 AM tool-updater), macOS SIGKILLs the next direct launch of each agent with
"Launch Constraint Violation" before it logs anything. That silently cost the
2026-09-20 newsletter and the 2026-09-21 plans. `scripts/lib/launchd-plists.test.mjs`
enforces this in CI.

## Deployment
- Vercel project connected to this repo
- Custom domain: southbaytoday.org
- stanwood.dev/south-bay redirects here permanently
- NEVER create files in a root `api/` directory — Vercel treats that as legacy serverless functions and routes all `/api/*` traffic away from Astro's `_render`, breaking every API route. All API routes must live in `src/pages/api/`.

## Prebuild gates (both must pass or Vercel fails the build)
- `scripts/check-home-locked.mjs` — Home tab import allowlist. Do NOT widen the
  allowlist to make a build pass; revert the addition instead.
- `scripts/check-tech-logos.mjs` — audits the committed tech logo manifest
  offline. **Fails** on a manifest entry pointing at a file that isn't in
  `/public/logos`, or on two unrelated ids resolving to byte-identical images
  (one wrong mark once served as 16 companies' logos for months). Ids that
  legitimately share a mark go in `SHARED_LOGO_GROUPS` in
  `scripts/lib/logo-audit.mjs` — the same module `fetch-tech-logos.mjs` uses, so
  the fetcher and the gate can't drift apart. It also prints non-fatal notes for
  manifest rows whose company is gone and companies with no logo yet.

## Email DNS
- Vercel DNS is authoritative; the intended ImprovMX + Resend/SES layout and change procedure are in `docs/email-dns.md`.
- DMARC must retain `p=reject`, `pct=100`, `adkim=r`, and `aspf=r`; `rua` routes aggregate reports to Postmark's free analyzer instead of a human inbox.
- Run `npm run verify:email-dns` after any email or DNS change.

The same 0a86b010 commit also unwired six section functions inside `TechnologyView.tsx`: `TechEventsSection`, `RecentlyFundedSection`, `FundingTicker`, `SvHistorySection`, `AnnualConferencesSection`, `GovTechCallout`. They're still defined in the file but never called — do NOT re-call them, do NOT extend the data that only they consume (`TECH_CONFERENCES`, `TECH_MILESTONES` window logic, etc.), and do NOT spend cycles "fixing" bugs in them. They render to nobody, so a fix to their date math, milestone windows, or conference rollover helps zero readers — automated sessions have burned full cycles on exactly this (`b5e570fa`, `c6a2e682`, `ead3fb69` all patched the dead SV-history / conference logic). The rendered Tech tab is: hero stats → Anchor Employers → `FundingHighlightsSection` (top 8 of `RECENTLY_FUNDED`) → Major Company Profiles → Hiring Pulse → `SpotlightHighlightsSection`. New funding entries DO render (via FundingHighlightsSection) — that's the right place for tech-coverage work.

Run `npm run audit-tech-urls` before and after tech-coverage work. It fetches every company card link in `tech-companies.ts` and flags MOVED (landed on a different domain) and DEAD results. MOVED is the useful signal: it catches acquisitions, rebrands, and lapsed domains that make a card factually wrong while the build stays green — the 2026-08-07 run caught Celestial AI (acquired by Marvell), Pure Storage (rebranded to Everpure), and Lambda Labs (now Lambda at lambda.ai). BLOCKED results are bot walls on live corporate sites; ignore them. When a company is acquired, remove it from `SCC_SPOTLIGHT` rather than re-pointing the link at the acquirer. City labels from funding aggregators are unreliable — verify HQ against the company's own press release dateline and boilerplate before adding a round, and record the reasoning as a comment in `RECENTLY_FUNDED` (there are several such notes already; Santa Clara County only, nothing north of the county line).

## Weather: Google primary — via the one canonical module
ALL reader-facing temperatures come from `src/lib/south-bay/weatherProvider.mjs`: Google Weather API → NWS → Open-Meteo, each only if the one before it fails. Consumers: `/api/weather`, `/api/plan-day`, `scripts/newsletter/lib.mjs`. Google is primary because Google is what readers and Stephen compare SBT against. From May to September 2026 we "fixed hot temps" four times by switching to whichever free feed matched Google that week (Open-Meteo → NWS, then an unmerged flip back), and each switch broke when the weather pattern changed. On 2026-09-22 NWS, GFS, ECMWF, and NBM all agreed on 86-91° for Campbell while Google said 81-83°; no free feed tracks Google. The full evidence table is in the module header.

- Do NOT reorder the chain, add a "more accurate" source, or add a direct Google/NWS/Open-Meteo forecast fetch anywhere else. `weatherProvider.test.mjs` fails the suite on any of those. Sun/UV-only Open-Meteo calls (SunUvCard) are fine.
- If the site disagrees with google.com, check `provider` on `https://southbaytoday.org/api/weather` first. Anything other than `"google"` means the key or the Weather API is broken (it uses `GOOGLE_PLACES_API_KEY`, or `GOOGLE_WEATHER_API_KEY` if set), and that is the bug to fix.
- Cost: the "Weather Usage" SKU gives 10k free calls/month, then $0.15/1k. `/api/weather` is CDN-cached for an hour per city and the module memoizes for 30 min per instance. Keep both caches.

## Events tab top is curated — no banners
**Guiding principle:** the search bar, filters, and event list must be reachable WITHOUT scrolling on a typical desktop or mobile viewport. Don't add anything above the controls panel (`.sb-events-controls`: day strip, search, category/area, quick filters) that pushes it below the fold.

Do NOT add heads-up banners, observance strips, school-calendar panels, holiday call-outs, or any other "above the filter bar" sections to `src/components/south-bay/views/EventsView.tsx`. Five banners were removed 2026-05-13 — SchoolHeadsUpBanner, SchoolYearEndgamePanel, HolidayHeadsUpBanner, HolidayPicksPreview, HeritageMonthBanner — because they pushed the filter bar off-screen (especially the school-dates content, which gets re-added on autopilot). The data files (`school-calendar.json`, `holidays.ts`, `heritageMonths.ts`) stay because they're used elsewhere — that's NOT a signal to re-wire a banner.

`WeekendPicksStrip` was the ONLY top-of-Events strip Stephen ever approved. It was removed in 0a86b010 (2026-05-22), so nothing sits above the controls now. Don't add strips, and restoring that one is Stephen's call. Routine work on filters, date pills, event cards, etc. is fine.

When you find an orphan component file or a data file with no visible UI, that is almost always intentional — either Stephen removed the rendering or the data is used elsewhere (social pipeline, day-plan generation, freshness checks). Do NOT "complete" it by wiring it in. Surface a 1-line note in your end-of-turn summary if you think something is genuinely missing, and let Stephen decide.
